# APISentry — How it works

## Architecture

```
Frontend (React + Vite, port 5213)
   │  axios → /api  (Vite proxy)
   ▼
Backend (FastAPI + Uvicorn, port 8213)
   ├─ auth (JWT + bcrypt)              SQLite (data/app.db)
   ├─ targets  (import / auth / scope)
   ├─ scans    → scan engine ──────────► live target over HTTP (httpx)
   │                 ├─ OWASP API Top 10 check modules
   │                 ├─ AI test generator (Gemini) + runner
   │                 ├─ severity-weighted scoring
   │                 └─ validation vs known-vuln list
   └─ reports  (Jinja2 HTML, ReportLab PDF)

Practice targets:  DemoPay (12130), VulnBank (12131)
CLI:  apisentry.py  → same scan engine, for CI/CD
```

## Scan pipeline
1. **Import & parse** — `services/spec_parser.py` turns an OpenAPI/Swagger or
   Postman collection into a normalised endpoint list (method, path, path-id
   params, query params, request-body fields).
2. **Scope guard** — `services/scope.py` blocks any scan whose host is not in
   `SCOPE_ALLOWLIST` (localhost by default); the API also requires an explicit
   "I am authorised" confirmation.
3. **Auth resolution** — `services/authprofile.py` logs in two test users (or
   uses supplied tokens) so access-control checks can compare user A vs user B.
4. **Discovery** — the engine collects object ids from list endpoints and a
   bounded numeric probe set, so object-level checks have real ids to test.
5. **Checks** — `services/scanner.py` runs each OWASP module against the live
   target and returns findings with evidence + a curl reproduction.
6. **Scoring** — `services/owasp.py` starts at 100 and subtracts a
   severity weight per finding (critical 8, high 6, medium 2, low 1), then maps
   the score to a grade (A ≥85, B ≥70, C ≥55, D ≥35, F <35).
7. **AI tests** — `services/ai_tests.py` asks Gemini for business-logic abuse
   tests constrained to an executable catalog (negative amount, foreign account,
   replay); the runner executes them live. Without a key, a deterministic
   built-in generator produces the same kinds of tests.
8. **Validation** — `services/validation.py` compares detected `vuln_key`s with
   the target's known-vulnerability list for a detection rate and false-positive
   count.

## Data
There is **no dataset**. All inputs are authored and committed:
- **Payload lists** and **fix recommendations** — `backend/app/services/payloads.py`.
- **Practice targets** and their **known-vulnerability lists** —
  `targets/demopay.py`, `targets/vulnbank.py`, and the matching
  `*_vulns.json` / `*_openapi.json` files (generated by `scripts/gen_specs.py`).

| Source | Licence | Committed |
|--------|---------|-----------|
| DemoPay / VulnBank targets (written for this project) | project code | Yes (`targets/`) |
| Payload & recommendation lists (written for this project) | project code | Yes (`backend/app/services/payloads.py`) |
| Known-vulnerability lists (written for this project) | project code | Yes (`targets/*_vulns.json`) |

No external dataset is downloaded and no model is trained — APISentry uses a
pretrained LLM (Gemini) via API plus a deterministic rule engine.

## Database schema (SQLite)
- **users** — id, email, password_hash
- **targets** — id, owner, name, base_url, endpoints, auth profile, known vulns
- **scans** — id, target, status, progress, score, grade, ai_generated
- **findings** — id, scan, check_id, severity, OWASP mapping, endpoint, evidence,
  curl, recommendation, fix snippet, vuln_key, source
- **ai_tests** — id, scan, name, category, endpoint, result, detail, generator
