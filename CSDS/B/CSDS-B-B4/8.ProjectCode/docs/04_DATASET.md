# 04 · Datasets

UPI Guardian uses three public datasets, one hand-written Indian scam-message set and one
seeded simulation. **All public datasets are committed in full** under `data/raw/` (total ≈ 91 MB,
largest file 45 MB), so nothing has to be downloaded to run or retrain.

| # | Dataset | Used for | Size | Licence | In the repository |
|---|---|---|---|---|---|
| 1 | Digital Payment Fraud Detection Benchmark | M1 behaviour model | 60.5 MB, 400,000 rows | CC0-1.0 | `data/raw/payment_fraud_benchmark/` (full) |
| 2 | UPI Transactions 2024 | Behaviour profiles for the simulator and cold-start defaults; label check | 29.8 MB, 250,000 rows | CC0-1.0 | `data/raw/upi_transactions_2024/` (full) |
| 3 | SMS Spam Collection | M2 SMS classifier | 0.5 MB, 5,572 messages | Kaggle lists "unknown"; the UCI original is CC BY 4.0 | `data/raw/sms_spam_collection/` (full) |
| 4 | Indian UPI-scam SMS set | M2 SMS classifier (English, Hindi, Telugu) | 815 messages | written for UPI Guardian | `data/raw/upi_scam_sms/` (full) + generator |
| 5 | UPI scenario simulation | M3 payment risk model | 641,672 payments (52 MB gzip) | generated | re-created by script; 5,000-row sample in `data/sample/` |

## 1. Digital Payment Fraud Detection Benchmark

- **Source:** https://www.kaggle.com/datasets/rohit8527kmr7518/digital-payment-fraud-detection-benchmark
- **Files:** `transactions_train.csv` (300,113 rows, 1 Jan – 30 Sep 2023) and
  `transactions_test.csv` (99,887 rows, 1 Oct – 30 Dec 2023).
- **Target:** `is_fraud` — 1.62 % in train, 1.99 % in test. A drift component is injected after
  month 6 (fraud becomes more velocity-driven).
- **Columns:** `transaction_id, transaction_time, customer_id, merchant_id, account_age_days,
  credit_score_band, kyc_level, avg_monthly_spend, merchant_risk_score, transaction_amount,
  payment_channel, device_type, is_international, ip_risk_score, txn_count_1h, txn_count_24h,
  failed_txn_count_24h, geo_distance_from_last_txn, amount_deviation_from_user_mean, is_fraud,
  post_auth_risk_score`.

**How it is used and cleaned**

| Decision | Why |
|---|---|
| Keep the provided time split; use September as validation | Chronological validation, as the dataset requires (no random K-fold) |
| Drop `post_auth_risk_score` | Target leakage (computed after the fraud decision) |
| Drop `ip_risk_score`, `credit_score_band`, `kyc_level`, `payment_channel` | The sandbox cannot observe them honestly; a *full-feature* reference model shows the cost is tiny (PR-AUC 0.355 vs 0.350) |
| `transaction_amount` → `log1p`; hour → sin/cos; device → one-hot | Scale / cyclic time / categorical encoding |
| Clip `account_age_days` to 30–2000 | The range seen in training |
| Blank `geo_distance_from_last_txn` for 50 % of training rows | Most sandbox users do not share location; the model learns to cope with a missing value |

The feature code is `backend/app/ml/features.py` (`m1_frame_from_benchmark`, `m1_row`).

## 2. UPI Transactions 2024

- **Source:** https://www.kaggle.com/datasets/skullagos5246/upi-transactions-2024-dataset
- **File:** `upi_transactions_2024.csv` — 250,000 synthetic UPI transactions for 2024.
- **Columns:** `transaction id, timestamp, transaction type (P2P / P2M / Bill Payment / Recharge),
  merchant_category, amount (INR), transaction_status, sender_age_group, receiver_age_group,
  sender_state, sender_bank, receiver_bank, device_type, network_type, fraud_flag, hour_of_day,
  day_of_week, is_weekend`.

**Label check.** `ml/profile_upi2024.py` trains Logistic Regression and XGBoost on Jan–Sep and
tests on Oct–Dec: PR-AUC **0.0027** and **0.0022** against a base rate of **0.0020**. Fraud rates
are flat across every feature, so `fraud_flag` looks randomly assigned. As planned, the dataset is
therefore used **only for behaviour profiles**: hour-of-day curve, amount distributions by merchant
category and transaction type (log-normal fits), weekend effect. The profiles are written to
`models/behaviour_profile.json`; only successful transactions are used.

## 3. SMS Spam Collection

- **Source (Kaggle mirror):** https://www.kaggle.com/datasets/uciml/sms-spam-collection-dataset —
  original: https://archive.ics.uci.edu/dataset/228/sms+spam+collection
- **File:** `spam.csv` (Latin-1 encoded), columns `v1` (`ham` / `spam`) and `v2` (text).
- **Cleaning:** strip surrounding whitespace, then drop the 414 duplicate texts (so the same text
  cannot appear in both train and test) → 5,158 messages (642 spam); `spam` → label 1.
- **Split:** stratified 60 / 15 / 25 (train / validation / test), seed 42.

## 4. Indian UPI-scam SMS set (written for UPI Guardian)

- **File:** `data/raw/upi_scam_sms/upi_scam_sms.csv` — generated by
  `scripts/generate_scam_sms.py` (seed 2026; re-running it produces the identical file).
- **What it contains:** 159 hand-written templates (84 scam SMS, 50 legitimate SMS, 12 deceptive and 13 ordinary collect-request notes) in **English, Hindi
  (Devanagari and Hinglish) and Telugu (script and romanised)**, each expanded into up to 6
  variants with fictional slot values (bank names such as "Bharat Union Bank", links such as
  `kyc-verify-now.top`, sandbox UPI IDs such as `kyc.helpdesk@upg`). No real bank, company or
  website names are used.
- **Columns:** `id, text, label (1 scam / 0 legitimate), category, language (en|hi|te), script
  (native|latin), template_id, kind (sms|collect_note)`.
- **Scam categories (12):** fake KYC / account block, refund / cashback, lottery / prize, job /
  task, electricity disconnection, collect-request trick, "sent by mistake", courier / customs,
  loan fee, OTP / PIN request, impersonation (family / police), investment doubling.
- **Legitimate categories (8):** bank debit / credit alerts, genuine OTPs ("never share"), bill
  reminders, deliveries, personal chat, promotions, "money received".
- **Collect-request notes:** short deceptive notes ("Refund for order … approve to receive") and
  ordinary ones ("Dinner split") for the F9 guard.
- **Counts:** 815 messages — 527 scam, 288 legitimate; 275 English, 270 Hindi, 270 Telugu.
- **Split:** by **template family** (30 % of templates for test, 25 % of the rest for validation,
  stratified by label × category × language), so no test message shares a template with training.

## 5. UPI scenario simulation (M3)

No public dataset contains UPI-specific context (new payee, community scam reports, a linked scam
SMS, a collect request disguised as a refund). `ml/simulator.py` creates it, deterministically
(seed 42), for **3,000 users over 12 months**:

- **Normal behaviour** from UPI Transactions 2024: per-user hour profiles, amounts by category,
  weekend effect, regular friends / shops / bills, saved contacts, **monthly family transfers**,
  new-payee payments (including large genuine deposits and some at night), legitimate collect
  requests between friends, and scam SMS the user checked but did not act on.
- **Scam episodes** across 12 typologies (the list above, plus QR-code tricks and taken-over
  contact accounts) with realistic variation: fresh, "mule" and long-standing compromised
  receiving accounts; escalating job / investment payments; night-time pressure; failed PIN
  attempts; victims reporting the account later; scam accounts spraying collect requests.
- **Signals from the real models:** each simulated payment's behaviour features are scored by
  **M1**; SMS and collect-note signals are the **M2** scores of *held-out* messages it never saw
  in training.
- **Label noise:** 2 % of scams are never reported; 0.02 % of genuine payments are falsely reported.
- **Output:** 641,672 payments, 0.54 % scams. Split by month: 1–9 train, 10 validation,
  11–12 test. Full file `data/processed/upi_scenarios.csv.gz` is re-created by
  `venv\Scripts\python ml\train_risk.py --regenerate`; a sample (1,000 scam + 4,000 genuine rows)
  is committed at `data/sample/upi_scenarios_sample.csv`.

## Download guide

The datasets are already in the repository. Use this only to restore or refresh them.

```bat
venv\Scripts\python scripts\download_data.py          :: verify, download only what is missing
venv\Scripts\python scripts\download_data.py --force  :: download everything again
```

The script verifies row counts, prints a line-ending-independent SHA-256 fingerprint of each
file and re-creates the Indian SMS set if it is missing. These datasets are public, so the script
falls back to Kaggle's public download endpoint when no token is configured.

### Optional: create a Kaggle API token

1. Go to https://www.kaggle.com and sign in (or create a free account).
2. Click your profile picture (top right) → **Settings**.
3. Scroll to **API** → click **Generate New Token** (or *Create New Token*).
4. Copy the token that is shown, open the project's `.env` file in Notepad and paste it after
   `KAGGLE_API_TOKEN=` (no spaces, no quotes). Save the file.
   - If Kaggle instead downloads a file called `kaggle.json`, place it at
     `C:\Users\<you>\.kaggle\kaggle.json` — that works too.
5. Run `venv\Scripts\python scripts\download_data.py --force` — it will use `kagglehub` with your token.
