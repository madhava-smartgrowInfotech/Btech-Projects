## 4. Architecture summary

- `src/` pure-Python pipeline (data_loader, preprocessing, demand_forecasting, feature_engineering, baseline_models, xgboost_model, domain_adaptation, evaluation, visualization, gemini_helper); `app.py` Streamlit UI (11 pages, original); `backend/` FastAPI layer (main.py 626 lines, state.py, gemini_api.py) over `src/`, in-memory single-user pipeline state; `frontend/` React UI (13 pages: landing, overview, upload, explore, demand, features, training, domain, evaluation, forecast, insights, about, 404).
- No database: pipeline state is a process-wide dict `S` guarded by an RLock; trained models are saved to `models/baseline_xgboost.joblib`, `adapted_xgboost.joblib`, `feature_info.joblib`.
- Pipeline: upload CSVs -> validate columns -> clean (parse dates, drop null ids, price<=0, exact duplicates) -> left-join articles (+customers) -> aggregate daily demand per article (rows = units) -> fill missing days with 0 -> features -> chronological split -> moving average / XGBoost (optional RandomizedSearchCV with TimeSeriesSplit) -> domain adaptation (logistic domain classifier, weight = p/(1-p) clipped at 20, weighted XGBoost) -> evaluation -> recursive 7/14/30-day forecast -> optional Gemini explanation.
- Features (31 model inputs): price, sales_channel_id, 6 label-encoded attributes (product_type, product_group, colour_group, department, section, garment_group), 14 calendar (year, month, day, day_of_week, week_of_year, day_of_year, quarter, is_weekend, is_month_start, is_month_end, month sin/cos, day-of-week sin/cos), 9 lag/rolling (lag 1/7/14/28, rolling mean 7/14/28, rolling std 7/28; shifted so the current day is excluded).
- XGBoost defaults: n_estimators 300, max_depth 8, learning_rate 0.05, subsample 0.8, colsample_bytree 0.8, squared error, random_state 42. Tuning: RandomizedSearchCV 10 iterations x 3 TimeSeriesSplit folds over n_estimators, max_depth, learning_rate, subsample, colsample_bytree, min_child_weight.
- Metrics: RMSE, MAE, safe MAPE (zero-actual rows excluded, count reported), R2; WAPE added offline.

## 8. Domain adaptation (importance weighting, the app's procedure, 5 XGBoost seeds)

Protocol (`backend/main.py::run_domain`): source model trained on all source-domain rows; target test = later 50 % of target dates; domain classifier = logistic regression (max_iter 1000, unscaled features, domain column excluded); weight = p/(1-p) clipped at 20; weighted XGBoost. Extra controls added offline: target-only oracle (first half of target), pooled source + target-train unweighted, shuffled weights, weights rescaled to mean 1, and a time-clean protocol (source restricted to dates before the target test window).

| Pair (source -> target) | Domain clf acc % | Source rows | Target test rows | RMSE before | RMSE adapted | Improvement % | Seeds improved | Shuffled-weights impr. % | Target-only RMSE | Pooled RMSE | Mean-1 weights impr. % | Time-clean impr. % |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Online -> Store (channel 2 -> 1) | 66.5 | 18854 | 6174 | 10.80 | 9.50 | +11.9 | 5/5 | +2.2 | 10.05 | 9.78 | +12.1 | -2.8 |
| Store -> Online (channel 1 -> 2) | 66.3 | 12240 | 9890 | 19.00 | 18.99 | +0.0 | 3/5 | +0.3 | 22.46 | 17.84 | +0.1 | -0.3 |
| Upper body -> Lower body | 93.3 | 16457 | 5162 | 13.90 | 14.80 | -6.5 | 0/5 | -5.2 | 18.21 | 13.51 | -6.0 | +3.0 |
| Lower body -> Upper body | 93.3 | 10012 | 8548 | 11.91 | 12.78 | -7.3 | 0/5 | -6.6 | 16.49 | 12.13 | -8.3 | +1.3 |
| Knitwear -> Trouser | 100.0 | 6250 | 2156 | 17.23 | 25.21 | -46.3 | 0/5 | -45.9 | 21.79 | 16.88 | +1.9 | -24.4 |
| Jersey Basic -> Blouse | 100.0 | 2138 | 916 | 12.20 | 16.99 | -39.4 | 0/5 | -44.4 | 13.55 | 11.54 | -38.7 | -19.4 |

- Adaptation as shipped improved RMSE on **2 of 6** pairs (range -46.3 % to +11.9 %, mean -14.6 %). With weights rescaled to mean 1 the mean is -6.5 %; under the time-clean protocol -7.1 % (mean-1 weights + time-clean: +0.2 %).
- **Finding 1:** the only clear gain (online -> store, +12 %) disappears (-2.8 %) when the source model is not allowed to train on dates inside the target test window - it came from time overlap, not from adaptation. Shuffled weights give +2.5 % on that pair, so part of the effect is noise.
- **Finding 2:** when the domain classifier separates the domains perfectly (department pairs, accuracy 100 %), p/(1-p) is ~1e-6..1e-3 for every source row (mean weight 5e-5 and 4e-4); XGBoost's `min_child_weight=1` can then never be met, the model stops splitting and predicts a constant (R2 about 0, RMSE +46 % worse). Rescaling the same weights to mean 1 removes the collapse (Knitwear -> Trouser +1.9 %).
- **Finding 3:** simply pooling source rows with the first half of the target domain, without weights, beats weighted adaptation on 5 of 6 pairs (the exception is online -> store, 9.78 vs 9.50); the target-only model is worse than the source-only model on 5 of 6 pairs (half of a small target domain is too little data).
- Logistic regression does not converge in 1000 iterations on the unscaled features (sklearn ConvergenceWarning on every run).
- App screenshot run (default Channel 1 -> Channel 2, seed 42): RMSE 18.983 -> 18.989 (-0.0 % worse), domain classifier accuracy 66.3 %.

## 14. Known defects / honest limitations found (product code untouched in this documentation run)

- Cleaning drops exact duplicate rows (11.6 % of the subset) although repeated identical H&M rows are real repeat purchases: demand is understated.
- `sales_channel_id` and `price` of the *target day* are model inputs (daily mode / mean of that day's transactions) - they are known planned inputs at best and partly leak same-day information; in recursive forecasts they are frozen at the last value.
- The domain label is the day's most frequent channel, but demand counts both channels, so 'channel domains' are mixtures.
- Source model for domain adaptation trains on dates that overlap the target test window (see time-clean result).
- Instance weights are not normalised; perfectly separable domains give weights ~1e-5 and XGBoost collapses to a constant.
- Domain classifier uses unscaled features; logistic regression does not converge (1000 iterations).
- Recursive forecast freezes week_of_year, day_of_year, quarter, month_start/end; error grows from WAPE 41 % (days 1-7) to 124 % (days 15-30).
- Absolute-time features (year, quarter, day_of_year) cannot extrapolate beyond the training dates; a lag/rolling-only model is better on the held-out window.
- Feature importance shown in the app is gain-based (not SHAP as in the base paper); inventory impact is not computed in the app; no cold-start mode.
- `src/baseline_models.train_lightgbm` passes pandas objects; with LightGBM 4.7 on this machine it crashed (access violation) unless lightgbm is imported before pandas/xgboost.
- Only 107 days, 300 best-selling articles and 2 sales channels: no multi-year seasonality, no new-store domain, no promotion data (H&M has none).
- Gemini AI Insights depends on an external service: during this run it returned 503 (high demand) and timed out, so the screen shows the error state in several captures.
