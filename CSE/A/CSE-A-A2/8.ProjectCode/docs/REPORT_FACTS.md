## 2. What the product is (read from the code)

- Flask 3.1.0 backend (`app.py` 296 lines, `auth.py` 181 lines, `train_models.py` 195 lines) + React 19 / Vite 8 frontend (`frontend/src`, 1,940 lines JSX+CSS, Neo-brutal design, Leaflet map, Recharts, framer-motion, GSAP). The original single-page Flask UI (`templates/index.html`, `static/js/script.js`) is still served at `/`.
- **No phone is attached**: sensor readings are *simulated* by `/api/simulate` from the same generator parameters as training; the React "Live monitor" polls one reading every 1.5 s. In a real deployment the phone's accelerometer / gyroscope / speed / GPS would supply the 11 features.
- Pipeline: reading (11 features) -> `StandardScaler` -> **accident detector** (RandomForest, 200 trees, depth 10, class_weight balanced) -> **severity predictor** (RandomForest, 250 trees, depth 12, class_weight balanced; 0 None / 1 Minor / 2 Moderate / 3 Severe). Gate: if the detector says no accident the severity is forced to 0 (`app.predict_from_features`). If model files are missing a rule-based fallback on `acc_magnitude` (<15 None, <28 Minor, <45 Moderate, else Severe) answers instead.
- Confirmation: only a **Moderate or Severe** result opens a 15-second countdown ("Possible accident detected"); live monitoring pauses; "I'm fine, cancel" (or Escape) cancels; at 0 s or "Send alert now" the app calls `/api/emergency`. Minor results are logged only.
- Emergency response: browser Geolocation (3 s timeout; falls back to a random point within ~6 km of the default Hyderabad location 17.3850, 78.4867), the three nearest hospitals by haversine distance from a **10-entry demo directory** (`data/hospitals.json`, Hyderabad), a drafted dispatch message (severity, confidence, coordinates, Google Maps link, nearest hospital + phone), alert id `RQ-<unix seconds>`, national emergency 112, ambulance 108 (traffic police 103 is in the UI). **Nothing is actually sent**: there is no SMS/e-mail/call gateway; the message is displayed. The UI states "this demo sends nothing to real responders".
- Accounts: `/api/auth/register|login|me|status`; werkzeug `generate_password_hash` (scrypt:32768:8:1) hashes in `data/users.json`; itsdangerous signed tokens (salt `resqai-auth`, 12 h expiry); 5 failed logins -> 5-minute lockout (HTTP 429); password 8-128 chars; name 2-60 chars; e-mail case-insensitive. `REQUIRE_AUTH=1` makes every `/api/*` route except `/api/health` and `/api/auth/*` demand a Bearer token (default 0 so the original Flask page keeps working). Secret from `SECRET_KEY` env or auto-generated `data/.secret`. `.env`, `data/users.json`, `data/.secret` are git-ignored.
- **Storage**: no database. Persistent state = two JSON files (`data/users.json`, `data/hospitals.json`) and four `.pkl` model files. Readings, predictions, event log (last 25), sensor chart (last 40 points) and alerts live only in React state / HTTP responses and are lost on reload. Alerts are not stored server-side.
- Frontend routes: `/` landing, `/login`, `/register`, then signed-in only `/monitor`, `/manual`, `/response`; 404 page; light/dark theme.

## 3. Data (synthetic - there is no real crash dataset)

- Source: `train_models.py` generates **12,000** events with `np.random.seed(42)`: kinds drawn with p = normal 0.60, harsh_brake 0.20, minor_crash 0.10, moderate_crash 0.06, severe_crash 0.04. Realised counts: normal 7,289 - harsh_brake 2,324 - minor 1,215 - moderate 725 - severe 447. Accident rate 19.89 %; severity counts None 9,613 / Minor 1,215 / Moderate 725 / Severe 447. Licence: self-generated, no external data. `measure_metrics.py` reproduces the generator exactly (`generator_reproduces_train_models = true`).
- 11 features: acc_x, acc_y, acc_z, acc_magnitude, gyro_x, gyro_y, gyro_z, gyro_magnitude, speed_before (km/h), speed_change (km/h), jerk (|.|). Crash events draw a random-direction acceleration spike (magnitude U(15,28) minor, U(28,45) moderate, U(45,80) severe) plus noise; gyro SD 1.5 / 2.5 / 4.0; speed_change U(10,40) / U(25,55) / U(45,100) of deceleration; jerk N(20,5) / N(35,8) / N(60,12). Normal driving: acc ~N(0,0.4) with acc_z ~N(9.81,0.3); harsh braking: acc_x ~N(-4.5,1.2), speed_change -U(10,35), jerk N(6,2).
- Split: `train_test_split(test_size=0.2, random_state=42, stratify=accident)` -> **9,600 train / 2,400 test**. Test: normal 1,463, harsh_brake 460, minor 233, moderate 156, severe 88 (accident 477 = 19.9 %). No validation split, no cross-validation in the shipped training script.
- Observed feature ranges per kind (whole set) - `acc_magnitude`: normal 8.7-10.9; harsh brake 8.8-13.2; minor 15.3-32.8; moderate 24.9-53.6; severe 42.4-87.9 m/s2. **Crash vs non-crash is separated by a single gap (13.2 -> 15.3 m/s2) in acc_magnitude**, which is why every classifier scores ~100 % on detection (see section 4). Severity classes overlap only at their boundaries (minor/moderate 24.9-32.8, moderate/severe 42.4-53.6).
- Not in the data: potholes, speed breakers, phone drops, sensor placement/orientation, real noise, GPS error, motorbike vs car, multi-impact crashes. No ground-truth injury data.

## 6. Objectives vs outcomes (the six in `6.OBJECTIVES&PROBLEM STATEMENT.docx`)
1. Collect and preprocess smartphone accelerometer / gyroscope / speed / GPS data - **partly**: a 12,000-event synthetic generator and a 11-feature pipeline; no real smartphone recordings were collected.
2. Distinguish accidents from potholes, speed breakers and hard braking - **partly**: hard braking handled (0 / 460 false alarms); potholes and speed breakers are not in the training data and a probe shows ~50 % of them flagged as accident (never Moderate/Severe).
3. Severity model (minor / moderate / severe) - **achieved on synthetic data**: accuracy 0.99958, macro-F1 0.99866 (5-seed mean 0.99875 / 0.99501).
4. GPS location + suitable nearby hospital - **achieved at demo level**: browser geolocation, haversine over a 10-hospital Hyderabad directory; no live hospital API, no capacity/specialty/traffic awareness.
5. Automated alert with location and severity to contacts and medical services - **partly**: dispatch message and ids generated and shown, 108/112 tap-to-call; **no SMS/call/e-mail is actually sent**.
6. Evaluate accuracy, false-alarm rate, end-to-end latency - **done** (section 4); alert path 56 ms mean on loopback plus the 15 s confirmation window; real network delivery not measurable.
Project-document extras: confirmation mechanism to reduce false alerts - achieved (15 s countdown; cancel by button or Escape); emergency dashboard - achieved (Response map screen).

## 7. Literature facts (verified from the PDFs in this batch)
- **Base paper (Wang, Liang, He, IEEE Access 2026)**: police-reported crash records of **Dongguan, China, 2019-2023, 30,442 records** (19,483 train / 4,871 validation / 6,088 test), tabular driver/vehicle/road/environment attributes, three tasks (injury severity 5 classes, fatal severity 5 classes, property loss 6 classes); multi-task FT-Transformer with uncertainty-weighted loss, SMOTE (k=1) on training only, Adam lr 1e-4, batch 500, early stopping patience 30; baselines XGBoost, LightGBM, CatBoost, MLP, DT, RF, SVM, KNN; SHAP interpretation. Results: injury severity accuracy 70.31 % (precision 60.16, recall 70.31, F1 64.48); fatal severity accuracy 90.38 % (P 87.19, R 90.38, F1 86.71); property loss accuracy 80.79 % (P 78.98, R 80.79, F1 79.18). Beat MT-CNN (Yang et al.: 0.58 / 0.82 / 0.62). Limits stated by the authors: single city, proprietary data, injury proxied by number of injured, no ordinal modelling, training/inference cost not compared. **It is a post-event analytics model on recorded crash reports - it does not detect a crash, use phone sensors, locate the crash or dispatch anything.** ResQAI borrows from it only the idea of grading severity and of reporting accuracy/precision/recall/F1 per class; it does **not** reuse the FT-Transformer, the dataset, SMOTE or SHAP. Datasets, tasks and label definitions differ completely, so the numbers cannot be compared as like for like.
- **GreenBox (Rocha, Soares, Valente, Pinto; arXiv 2606.16468, Jun 2026)**: Arduino Uno + SIM7600G-H GSM/GPS shield; four push-buttons as impact sensors, MPU-6050 for rollover (> 70 degrees via arctangent), two water-level sensors, relay to cut the engine; SMS with location and speed to preset contacts; owner can cancel a false detection by SMS. Evaluation is qualitative ("alert SMS in a matter of seconds", on-road GPS/speed check) - **no accuracy, precision or latency numbers are given**. No ML.
- **CIRS (Ayesha, Aslam, Zaheer, Khan; Sensors 2025, 25(18), 5845)**: multi-agent framework - YOLOv11 accident detection on camera frames, VideoLLaMA3 scene description, localisation and dispatch agents; custom dataset 5,200 accident + 4,800 non-accident frames; YOLOv11 top-1 accuracy 86.5 %, precision 0.866, recall 0.856, F1 0.861; 128 of 1,044 non-accident frames falsely classified as accident; VideoLLaMA3 BLEU 0.0755, METEOR 0.2258, ROUGE-L 0.3625. Vision-based (fixed CCTV), different sensing modality from ResQAI.

## 9. Honest summary of what the numbers mean
- All accuracy figures are on **synthetic** data drawn from the same distribution as training; near-perfect scores show the classes are well separated by construction, not that the system would score this on real roads. A single acc_magnitude threshold gives the same detection result.
- Real-world claims that **cannot** be made: detection rate on real crashes, false-alarm rate on real roads, pothole/speed-breaker rejection, battery/CPU cost on a phone, GPS accuracy, SMS/call delivery time, multi-user capacity.
- What can be claimed: the pipeline works end to end (sensor-style reading -> detection -> severity -> 15 s confirmation -> location -> nearest hospital -> drafted dispatch message) with ~56 ms of compute on loopback; the severity model is better than a threshold rule on the synthetic data; the models degrade gracefully up to ~10 % sensor noise and collapse beyond ~50 %; authentication behaves correctly; input validation has gaps (section 5).
