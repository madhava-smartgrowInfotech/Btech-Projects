## 2. What the system is
- A web application that predicts the risk class (**Positive (High Risk)** / **Negative (Low Risk)**) of **four conditions - diabetes, heart disease, liver disease, kidney disease** - from routine clinical values entered by the user.
- For each condition four classifiers are trained - **Logistic Regression (max_iter 1000), Decision Tree (max_depth 6), Random Forest (200 trees, max_depth 8), SVM (RBF, C=1, probability=True)** - on StandardScaler-scaled inputs. The model with the highest hold-out **F1** is saved (`models/<d>_model.pkl`, `_scaler.pkl`, `_features.pkl`) and served.
- Layers: `generate_data.py` (synthetic CSVs) -> `train_models.py` (train/evaluate/save, writes `models/training_report.json`) -> `app.py` (Flask pages, model bundles, field metadata) -> `backend/main.py` (FastAPI JSON API that imports `app.py`; same prediction maths) -> `frontend/` (React 19 + Vite 8, React Router, Recharts, three.js hero, framer-motion).
- There is **no database, no user accounts and no stored patient data**: models are pickle files, datasets are CSV files, the report is JSON. Predictions are not stored.
- The UI shows the *predicted-class confidence* (`max(predict_proba)`, 50-100 %), the model name and that model's hold-out accuracy, plus a not-a-diagnosis notice. **Per-prediction feature explanations are NOT implemented** in the application (objective 6 is only partly met - see section 12).
- Frontend routes: `/` landing; `/app` overview; `/app/predict/:disease` (diabetes, heart, liver, kidney; 'Positive sample' / 'Negative sample' buttons pre-fill a real row of the CSV); `/app/models` (metric bars + sortable table); `/app/data` (dataset cards, class balance, synthetic-data warning); `/app/about`; 404 page. Dark and light themes; responsive down to a 390 px phone.
- Input handling: the form checks required/numeric, shows a warning when a value is outside the training range of that feature; the API returns HTTP 422 with a message for missing / non-finite values and 404 for an unknown disease.

## 3. Datasets (IMPORTANT: synthetic)
- The four CSVs in `data/` are **synthetically generated** by `generate_data.py` (numpy seed 42, N = 2,000 rows each, 8,000 rows in total): feature values are drawn from clipped normal / exponential / uniform distributions with medically informed means, a hand-written linear *risk score* is passed through a sigmoid, thresholded at 0.5, and **8 % of the labels are then flipped at random** (`add_noise_labels(noise=0.08)`). The README and the app's Datasets page both say so.
- Consequence 1: the label is a *known linear function of the features plus 8 % noise*, so **no classifier can exceed about 92 % accuracy** on fresh draws of this data (the noise ceiling), and a linear model is the correct model family. Logistic Regression's 88.3-91.8 % hold-out accuracy is therefore close to the ceiling; this says the pipeline works, not that it diagnoses real patients.
- Consequence 2: the reported metrics are **not clinical performance** and must not be compared with published results on real data without saying so.
- Source / licence: self-generated (no third-party data, no licence issue). No missing values, no duplicate rows (checked), so the objective 'handle missing values / outliers' has nothing to act on in the shipped pipeline - **no imputation or outlier handling code exists** (the real-data check below does impute with the median).
- Preprocessing actually implemented: StandardScaler fitted on the training part only; stratified 80/20 split; nothing else (no feature selection, no SMOTE, no class weights, no hyper-parameter search).

## 11. Testing and performance
- `scripts/smoke_test.py`: 27 PASS lines (health, list, report, datasets, per-disease form metadata, 2 samples x 4 diseases predicted, invalid input 422, unknown disease 404) - all passed.
- `scripts/api_tests.py`: **41/41 checks passed** - functional (every endpoint, both classes, all four diseases), consistency (API prediction equals direct `model.predict` on 40 sampled rows; same input twice -> same output), validation (missing field, empty body, 'abc', 'nan', 'inf', null, empty string -> 422; numeric string accepted; extra field ignored; unknown disease 404; malformed JSON 422; wrong method 405; unknown route 404), sanity (extreme low-risk vs high-risk diabetes input).
- Observations (not failures): the API accepts physiologically impossible values (glucose 100,000 mg/dL -> High Risk 60.94 %; age -5 -> High Risk 74.61 %): there is **no clinical range validation**, only a UI warning when a value is outside the training range.
- `scripts/capture_screens.py` (the 12 base screens, fails on console errors / failed requests) and `scripts/capture_extra.py` (screens 13-19) drive the real app in Chrome with Playwright.
- There is **no pytest suite, no frontend unit tests, no load test beyond the one below, and no security test** (no authentication exists to test; CORS allows only localhost:5303 / 127.0.0.1:5303).

## 13. Base paper (for comparison; NOT a like-for-like comparison)
Alam et al., IEEE Access 2026: UCI **thyroid** dataset (ann-train + ann-test merged, **7,200 samples, 21 features**, three classes Normal / Hypothyroid / Hyperthyroid; class counts as stated in the paper 6,666 / 368 / 166), five classifiers (SVC, Random Forest, Extra Trees, AdaBoost, CatBoost), **nested cross-validation** (outer stratified 5-fold, inner 3-fold grid search on accuracy), full feature set and a TOP-10 consensus set (TSH, FTI, T3, TT4, T4U, on thyroxine, query hypothyroid, psych, thyroid surgery, sex), SHAP + counterfactual explanations; Random Forest 0.996-0.997 accuracy/F1, AUC 0.999-1.000; SVC 0.965-0.967 accuracy, AUC 0.990-0.992; SMOTE tried and rejected (minority recall +<2 %); limitations: class imbalance, no external validation. Differences from this project: one disease vs four; real vs synthetic data; three-class vs binary; nested CV + tuning vs a single split with fixed settings; SHAP/counterfactual explanations vs none in the app. The project reuses the *idea* of comparing several classical classifiers with held-out evaluation and extends the scope to four diseases behind one interface; it does not reproduce the thyroid experiment.

## 15. Honest gaps and findings to state in the documents
- All headline accuracies (88.3-91.8 %) are on synthetic data whose labels are a known linear rule plus 8 % flipped labels; the noise ceiling is about 92 %. They are not clinical results.
- On real public data the same algorithms reach 71.8-98.8 % depending on the disease (section 10); the shipped models do not generalise to real records at the 0.5 rule (liver below the majority baseline).
- Model selection used the test set and one split; 5-fold CV and 10 seeds show Logistic Regression is the best (or tied-best) model for all four diseases, including diabetes where SVM was shipped.
- ROC-AUC was never computed by the project's own training script (objective 4); no missing-value / outlier handling (objective 2); no per-prediction explanation and no recommendations (objective 6 and the abstract).
- No hyper-parameter tuning, no calibration, no probability meaning: the shown 'confidence' is max(predict_proba) of the predicted class.
- No authentication, no persistence, no audit log; no pytest suite; no clinical validation, no ethics approval, no external validation.
- Base-paper comparison is qualitative only (different disease, data and protocol).
