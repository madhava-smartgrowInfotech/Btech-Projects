## 2. What the system is (architecture summary)

- Tiers: React SPA (Vite proxy `/api` -> backend) -> FastAPI app (`app/api_v1.py` JSON API + legacy Jinja HTML routes in `app/main.py`) -> services (`election_service`, `voting_service`, `audit`) -> SQLite via SQLAlchemy 2 (`data/aegisballot.db`) with the **local permissioned ledger** (`app/ledger/ledger.py`).
- Identity: `IdentityVerificationProvider` interface + `DemoAadhaarProvider` (12 digits, Verhoeff checksum, salted+peppered SHA-256 lookup in `voter_profiles`; does NOT contact UIDAI). Aadhaar numbers are synthetic, generated with a valid Verhoeff check digit (`generate_valid_aadhaar`).
- Vote flow: login (Argon2id, server-side session cookie `aegis_session`, CSRF token header) -> verify Aadhaar -> one-time authorization token (256-bit, SHA-256 stored, 10 min expiry, UNIQUE per election+voter) -> cast: candidate id encrypted with AES-256-GCM (12-byte random nonce, single election key) -> transaction hash = SHA-256 of canonical JSON {election_id, ballot_id, encrypted_payload, nonce, timestamp}, signed Ed25519 with a system key -> `propose_block` (one transaction per block, 3 validators, quorum 2 of 3, each approving validator signs the block hash with Ed25519) -> `ballots` row (no voter id) + `voter_participation` row (voter id + ballot id, UNIQUE per election+voter) -> receipt (ballot id, tx hash, block index, block hash).
- Ledger: block hash = SHA-256 of canonical JSON {block_index, timestamp, previous_hash, merkle_root, sorted tx hashes}; "merkle root" = SHA-256 of the concatenated sorted tx hashes (a flat hash, not a binary Merkle tree); genesis block at index 0 with previous hash 64 zeros. `validate_chain` recomputes merkle root, block hash and previous-hash links for every block.
- One-vote enforcement in four layers: (1) eligibility row, (2) `voter_participation` UNIQUE(election, voter), (3) single-use authorization UNIQUE(election, voter) + `is_used`, (4) ledger nonce / tx_hash uniqueness check in `propose_block`.
- Roles: ADMIN, VOTER, AUDITOR (RBAC through dependency functions; HTML routes and `/api` routes). Rate limit: 10 logins / 60 s and 15 verifications / 60 s per client IP (in-memory).
- Audit log: `audit_logs` rows for login, verification, authorization, cast, election/candidate changes, integrity checks and tamper tests.
- Database: 13 tables (`app/models/models.py`): users, voter_profiles, elections, candidates, voter_eligibility, voting_authorizations, ballots, voter_participation, ledger_blocks, ledger_transactions, validator_nodes, audit_logs, benchmark_runs.
- Source size (non-blank lines): backend `app/**/*.py` 2091, tests 372, scripts (`capture_screens.py`, `smoke_test.py`) 376, frontend `src/**/*.ts(x)` 5281.
- Frontend stack (package.json): React 18.3, React Router 7, TanStack Query 5, Tailwind CSS 4, Radix UI, Recharts 3, Framer Motion, GSAP, Lenis, Sonner, TypeScript 5.9, Vite 8. Pages: Landing, Login, Admin (Dashboard, Elections, ElectionDetail, Benchmarks), Voter (MyElections, VoteFlow), Auditor (Auditor, BlockDetail), Results, NotFound.

## 4. Data

- Benchmark data: `run_benchmark` generates synthetic voters (Argon2-hashed passwords, Verhoeff-valid Aadhaar numbers) in the measuring database; no real personal data anywhere.
- Licence/source: generated locally; names in `seed.py` are common Indian given names combined arbitrarily. No licence issue.
- Split: not applicable (no learned model). This is a systems/security project, so the evaluation is functional tests, tamper-detection tests and performance benchmarks, not accuracy/F1.

## 7. Tamper-detection study (measured)

Chain of 361 blocks (360 votes) in a scratch database; each case is applied inside a transaction and rolled back. "Product check" = the existing `validate_chain` (also used by the auditor page and `/api/chain/verify`). "Stricter audit" = a check implemented only in `scripts/run_experiments.py` (NOT in the product) that additionally verifies validator signatures, recomputes every transaction hash, verifies the system signature and cross-checks `ballots` against the ledger.

| # | Tamper | Product check | Stricter audit | Tally changed |
|---|---|---|---|---|
| T1 | block_hash of one block replaced | DETECTED (block_hash) | detected (validate_chain) | - |
| T2 | previous_hash of one block replaced | DETECTED (block_hash) | detected (validate_chain) | - |
| T3 | merkle_root of one block replaced | DETECTED (merkle_root) | detected (validate_chain) | - |
| T4 | timestamp of one block shifted by one hour | DETECTED (block_hash) | detected (validate_chain) | - |
| T5 | tx_hash of one ledger transaction replaced | DETECTED (merkle_root) | detected (validate_chain) | - |
| T6 | encrypted_payload in ledger_transactions replaced by another ciphertext | **missed** | detected (tx_hash_recompute) | - |
| T7 | encrypted_choice of one row in ballots replaced by a vote for another candidate (tally source) | **missed** | detected (ballots_vs_ledger) | yes |
| T8 | transaction removed from a block | DETECTED (merkle_root) | detected (validate_chain) | - |
| T9 | a block and its transaction removed from the middle of the chain | DETECTED (previous_hash) | detected (validate_chain) | - |
| T10 | newest block and its transaction removed | **missed** | detected (ballots_vs_ledger) | - |
| T11 | validator_signatures replaced with random hex | **missed** | detected (validator_signatures) | - |
| T12 | attacker edits a ballot and recomputes every hash from that block to the tip | **missed** | detected (validator_signatures) | - |
| T13 | both ballots and ledger edited consistently, hashes recomputed (signatures untouched) | **missed** | detected (validator_signatures) | yes |

Product check detects 7 of 13 cases; the stricter audit detects 13 of 13. Baseline (no tampering): both report valid. Cost: product check 146.18 ms vs stricter audit 787.5 ms on the 361-block chain.

Important findings from this study:

- `validate_chain` never verifies validator signatures and never recomputes a transaction hash from the transaction fields, so editing a ledger payload (T6), or editing it and recomputing all hashes (T12, T13), passes the product check. Editing the `ballots` table (T7), which is the **source of the tally**, also passes, and changes the tally.
- Dropping the newest block (T10) is not detected by the product check (a chain with fewer blocks is still a consistent chain).
- The "tamper test" button (`tamper_test_clone`) does not run `validate_chain` on a modified copy: it overwrites a hash in memory and returns `detected: True` from a hash-link comparison, so it demonstrates the idea, not an independent test (the `tampered_block_detection` unit test does tamper with the real DB and validates).
- All 3 validator private keys live in `data/validators.json` on the same server, so a party with write access to that file can also forge signatures; the quorum is a simulation of distribution, not distributed trust.

## 10. Gaps and honest limitations (state these plainly in every document)

- No real UIDAI/Aadhaar integration: identity check is a local, synthetic registry (`DemoAadhaarProvider`); no biometric or OTP factor.
- The ledger is a local permissioned simulation: 3 validators are in-process keys stored in `data/validators.json`; no network of nodes, no consensus protocol messages, no smart contracts, not Ethereum. One transaction per block.
- "Merkle root" is a flat hash of the sorted transaction hashes, not a Merkle tree (no inclusion proofs).
- `validate_chain` does not verify signatures or recompute transaction hashes; the tally reads the `ballots` table, which the ledger check does not cover (see section 7).
- Ballot secrecy is partial: `voter_participation` stores voter id and ballot id together, the ballot ciphertext is under one server-held AES key (README says per-election; `config.py` generates one key), and the admin can read a live tally of an open election. A database + key holder can link voters to choices.
- The key `data/secrets.json`, validator keys and the system key are plain files; sessions are in memory (lost on restart); rate limiting is per IP and in memory (10 logins/min shared by everyone behind one IP).
- No TLS in the shipped configuration (plain HTTP), cookie has no `Secure` flag; the batch abstract lists TLS and bcrypt - the build uses Argon2id and HTTP.
- "Async" benchmark batches are sequential (code-verified), so no concurrency result exists; concurrent voting (parallel block creation, `block_index` UNIQUE races) was not tested.
- Benchmarks ran on a shared PC; the base paper's numbers cannot be compared like for like (different chain, language, hardware, per-transaction vs per-vote definition).
- No load test over HTTP beyond 27 voters (login rate limit), no penetration test, no usability study with real voters, no accessibility audit.
- No external dataset or ML component exists, so accuracy/F1 do not apply; the evaluation is functional correctness, tamper detection and latency.
- Base paper figures are charts without tabulated values; its per-transaction times (~2 s registration, ~3-4 s voting on a Geth test chain) were read from Figures 6 and 9 by eye and are quoted as approximate.
