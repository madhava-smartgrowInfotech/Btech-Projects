## What the project is
- Product **AgriVision**: React 18 + Vite + TypeScript + Tailwind SPA (12 page components, ports 5416) -> FastAPI layer `backend/main.py` (16 routes, port 8416) that imports the ORIGINAL Flask product `agrivision/` (`inference.py`, `disease_db.py`, `app.py` for `init_db`) -> one SQLite file (`users`, `results`) + `agrivision/static/uploads/`. Demo login `demo@agrivision.ai` / `demo1234`. Launch: `run.bat`.
- **Diagnosis engine in the shipped product = a colour/texture heuristic** (`agrivision/inference.py`): resize 256, shares of green/brown/yellow/dark/white pixels + global std, a hand-written score per class, hash jitter, confidence squeezed into 0.62-0.99. `agrivision/models/` is empty so no network is loaded. If `models/plantdoc_cnn.h5` + `labels.json` (from `agrivision/train.py`) were present the same function would use the Keras model (`try_load_model`, `PLANTDOC_MAP` maps the 28 PlantDoc folders to the 38 canonical classes). The UI says "Heuristic engine" on every result and in the sidebar.
- Knowledge base `disease_db.py`: 38 classes (PlantVillage/PD36-C label set, 14 crops, 12 healthy), 26 curated disease cards + 5 generic kinds (fungal/bacterial/viral/pest/healthy); each card: symptoms, lifecycle, severity (high 12 / medium 14 / none 12), 3 treatments (chemical, organic, cultural, with rupee cost text), prevention, urgent flag.
- Multilingual = interface strings only in English/Hindi/Marathi (44 keys in `frontend/src/lib/i18n.tsx`); disease and treatment text stays English.
- NOT implemented although the batch abstract proposes them: yield prediction, weather recommendations (OpenWeatherMap), fertiliser-dose advice (only treatment text), voice interface, administrative dashboard, a trained CNN inside the app, validation of advice by an agronomist. Say so plainly in scope, limitations, results (objectives vs outcomes), conclusion.

## The honest story (state it plainly and consistently everywhere)
1. The system is built and works end to end (12 screens, 16 API routes, history, exports, analytics, 3-language interface, HMAC-signed bearer-token login). `smoke_test.py` 39/39 pass; `edge_tests.py` 51 checks, 46 pass, 5 reproduce defects; `ui_checks.py` 55 passed in the frontend session (not re-run here). API detect call median 23 ms round trip on 127.0.0.1 (p95 82 ms).
2. **But the engine it ships does not diagnose**: on the 236 PlantDoc test photos, with the crop chosen, top-1 = 9.1 +/- 1.0 % (10.6 % with the hash seed run.bat uses), top-3 34.9 %; crop left on 'general' 1.3 %. Chance is 36 % when the crop is known, 2.6 % on 38 classes; always answering the most frequent class gives 5.1 %. Healthy-vs-diseased accuracy 35.1 % is below the 61.9 % of always answering "diseased". Its displayed confidence (mean 95 %) says nothing about correctness. Five of the demo scans in the screenshots show visibly lesioned leaves called "healthy 97.2 %".
3. 32.2 % of test photos get no answer with the crop chosen, because crop options with fewer than 3 candidate classes (10 of 19 options) make `_heuristic_predict` raise IndexError and the API reply is HTTP 400 "UNREADABLE_IMAGE" (screenshot 16). The unit/API edge tests reproduce it.
4. The compact CNN of `train.py` (189,655 parameters, not the ~1.1M claimed in its docstring) trained here, 3 seeds, held-out validation: accuracy 12.0 +/- 0.5 %, macro-F1 0.086; it under-fits (training accuracy 22 %); the shipped protocol (test folder as validation) gives 13.6 %, no LR decay 12.7 %. A MobileNetV2 reference (ImageNet weights, head + top 30 layers fine-tuned, 3 seeds): accuracy 50.3 +/- 0.9 %, macro-F1 0.490, top-3 79.8 %, healthy-vs-diseased 88.8 %. A random forest on colour/texture features: 21.6 %. These are the real numbers; MobileNetV2 and the compact CNN are NOT part of the shipped app.
5. Dataset: PlantDoc (web-scraped field photos), 2,342 train + 236 test, 28 train folders / 27 test folders, CC-BY-4.0. Small, imbalanced (2 to 180 per class), noisy. The PlantDoc authors themselves report 44.5-70.5 % (cropped leaves) and 13.7-29.7 % (raw photos, VGG16) - the project's MobileNetV2 result is in that range, which is the realistic level for this data without cropping or more data.
6. Defects found and reported (never hide, use these IDs): **D1** 10 of 19 crop options crash the heuristic (HTTP 400); **D2** the three displayed scores add up to more than 100 % (max 112 %) and the confidence is a calibration-free score; **D3** the default token-signing secret `agrivision-dev-secret-change-me` is public (a forged token is accepted unless `AGRIVISION_SECRET` is set); **D4** no rate limiting on login; **D5** `train.py` validates on the test folder and mislabels the two grape classes there (27 test class names vs a 28-class model; grape_leaf and grape_leaf_black_rot labels shifted by one); **D6** `train.py` docstring says ~1.1M parameters, the model has 189,655; **D7** heuristic latency padded by a constant +40 ms in `predict()`.
7. Base paper (Foliagen, Pakka et al., IEEE Access 2026): a framework that *generates* annotated foliage images from single-leaf photos (rembg background removal, phyllotactic leaf placement, disease rate gamma 1-20 %) to train and fine-tune classifiers (VGG19, ResNet50, DenseNet121, Swin, CBAM-ConvNeXt), soybean and tomato, up to 98 % accuracy on natural foliage with 5 % real images added. This project does NOT implement Foliagen: the batch document's own note says the gap is "joining reliable classification to actionable, multilingual treatment and fertiliser recommendation", and that is what the project builds (diagnosis + advice + web app). Compare only qualitatively; say plainly that task, crops, data and hardware differ. Companion papers: PD36-C [2] (99.53 % on lab-style 87k images), Kanakala and Ningappa [3] (CNN 96.4 % val), PlantDoc [4].
8. Novelty/contributions (honest, modest): (i) an end-to-end farmer-facing application joining diagnosis, 38-class knowledge-based treatment advice, history, exports, analytics and a three-language interface in one deployable stack that runs on a CPU laptop with one command; (ii) an explicit, tested contract between a FastAPI layer and the legacy Flask product (shared DB and uploads, same detection and knowledge modules, no reimplementation); (iii) a reproducible, seeded benchmark on PlantDoc that measures the shipped heuristic, the shipped CNN recipe, a transfer-learning reference and classical baselines under one protocol, with defects documented; (iv) findings: the heuristic is no better than chance, the shipped training script has label and selection defects, field photos need transfer learning (50 % vs 12 %). Do not claim improvements that the data does not show.
9. Gaps to state: no trained model in the product; accuracy far below usable (50 % best); advice not agronomist-validated and dosage text is generic/curated, not region-specific; no fertiliser/yield/weather; PlantDoc only (no own photos, no user study, no load test, no field trial, no offline mode); one seed for the shipped-protocol and tuned-CNN runs; 3 seeds elsewhere, no significance test; UI checks not re-run; the 4 batch-survey papers [25]-[28] cannot be verified.
